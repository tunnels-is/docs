# Security Architecture

Tunnels.is implements a multi-layered security architecture with post-quantum cryptography, certificate-based authentication, and device-token authorization.

---

# Core Concepts

### Deployment Architectures

Tunnels.is supports two deployment models:

**Single Server (AUTH + VPN Combined)**
```md
Single server handles both authentication and VPN tunneling.
Clients authenticate and connect to VPN on the same server.
```

**Distributed (Separate Control and VPN Servers)**
```md
Control Server: CertPem/KeyPem
- Handles user authentication and management

VPN Server:
- Own CertPem/KeyPem: TLS connections
- SignPem: control server's public key for verification
```

The control server manages all users, devices, and groups. VPN servers handle tunnel traffic and validate user connections using signatures from the control server.

### Certificates and Keys

The system uses PEM-encoded certificates and keys:

#### CertPem & KeyPem - Server Identity

```md
CertPem: Public certificate for TLS/HTTPS
KeyPem: Private key for TLS
Algorithms: ECDSA P-521 (auto-generated) or RSA-4096 (user-provided)
Validity: 10 years (configurable)
```

#### SignPem - Control Server Verification

```md
Purpose: VPN server verifies control server signatures
Content: control server's public key/certificate
Used When: Control and VPN are separate servers
```

In single-server mode, the server uses its own key pair for both TLS and signature verification. In distributed mode, `SignPem` holds the control server's certificate.

#### Certificate Distribution

Server certificates are distributed through the control database. When a server entry is created in the admin UI, the server's `CertPem` contents are stored alongside the server record.

**Distribution Flow:**

```md
1. Admin creates a VPN server entry in the control database and provides the server's certificate
2. Client queries control server for available VPN servers
3. Client receives server certificate and pins it
4. Client uses pinned certificate for all TLS connections
```

This eliminates the need for a certificate authority. Each VPN server's certificate is directly pinned by clients through the trusted control server.

### Cryptographic Primitives

#### Post-Quantum TLS

All HTTPS API connections use TLS 1.3 with a post-quantum hybrid key exchange:

```md
- TLS layer: X25519MLKEM768 hybrid key exchange (ML-KEM-768 + X25519)
- Both client and server prefer X25519MLKEM768 in their TLS configuration
- Provides security against both classical and quantum computers
```

The server TLS config (`server/main.go`):

```go
APITLSConfig.Store(&tls.Config{
    MinVersion:       tls.VersionTLS13,
    CurvePreferences: []tls.CurveID{tls.X25519MLKEM768},
    Certificates:     apiCerts,
})
```

The client HTTP transport (`client/api.go`):

```go
client.Transport = &http.Transport{
    TLSClientConfig: &tls.Config{
        MinVersion:         tls.VersionTLS13,
        CurvePreferences:   []tls.CurveID{tls.X25519MLKEM768},
        InsecureSkipVerify: !skipVerify,
    },
}
```

#### Tunnel Encryption

VPN tunnel traffic uses a hybrid post-quantum encryption scheme built on the `crypt` package:

```md
- Key exchange: X25519 ECDH + ML-KEM-1024 (hybrid post-quantum)
- Data encryption: Configurable AEAD (AES-128-GCM, AES-256-GCM, or ChaCha20-Poly1305)
- Signature verification: RSA-PSS or ECDSA (server handshake is signed)
- Implementation: github.com/tunnels-is/tunnels/crypt
```

The server and client derive shared secrets from both X25519 and ML-KEM-1024, combining them for the symmetric data encryption key.

# Authentication Protocols

### User Authentication

#### Registration and Login

User registration (`server/handlers.go`):

```md
- Password requirements: 10-200 characters
- Password hashing: bcrypt with cost factor 13
- Device token: UUID-based per-device identifier
- Trial period: Automatic 1-day trial for new users
```

User login (`server/handlers.go`):

```md
1. Password verification via bcrypt comparison
2. TOTP-based two-factor authentication
3. Device token generation (unique per device)
4. Sensitive data removed from response
```

#### Two-Factor Authentication

```md
Algorithm: TOTP (Time-Based One-Time Password)
Library: github.com/xlzd/gotp
Backup Codes: Recovery codes for account access
Server Secret: Configured via TwoFactorKey setting
```

# Connection Flow

### Handshake Protocol

```md
[Client]                    [Control Server]               [VPN Server]
   |                              |                              |
   |--1. POST /v3/user/login ---->|                              |
   |   (email, password, TOTP)    |                              |
   |                              |                              |
   |<--2. DeviceToken ------------|                              |
   |                              |                              |
   |--3. POST /v3/session ------->|                              |
   |   (DeviceToken, UserID,      |                              |
   |    ServerID, EncType)        |                              |
   |                              |                              |
   |      [Verify User,           |                              |
   |       Sign Payload]          |                              |
   |                              |                              |
   |<--4. SignedConnectRequest ---|                              |
   |   (Signature + Payload)      |                              |
   |                              |                              |
   |   [Generate X25519 +         |                              |
   |    ML-KEM-1024 keys]         |                              |
   |                              |                              |
   |--5. POST /v3/connect --------|----(TLS)-------------------->|
   |   (SignedRequest +            |                              |
   |    X25519PeerPub +            |                              |
   |    Mlkem1024Encap)            |                              |
   |                              |     [Verify Signature,       |
   |                              |      Init Encryption,        |
   |                              |      Allocate Ports]         |
   |                              |                              |
   |<--6. ServerConnectResponse --|----(TLS)---------------------|
   |   (X25519Pub, Mlkem1024Cipher,                              |
   |    InterfaceIP, DataPort,                                   |
   |    StartPort, EndPort,                                      |
   |    Routes, DNS, Networks)                                   |
   |                              |                              |
   |   [Finalize Encryption,      |                              |
   |    Create TUN Interface]     |                              |
   |                              |                              |
   |--7. Encrypted UDP Traffic ---|----(UDP DataPort)----------->|
   |<--8. Encrypted UDP Traffic --|----(UDP DataPort)------------|
```

**Key Security Steps:**

```md
- Step 1: bcrypt password verification + TOTP 2FA
- Step 2: UUID device token issued per device
- Step 3: Controller validates user authorization and signs the connect request
- Step 4: Signed payload includes creation timestamp (240-second expiry)
- Step 5: Client sends signed request + X25519/ML-KEM-1024 key material to VPN server
- Step 6: VPN server verifies controller signature, performs key exchange, allocates ports
- Steps 7-8: Symmetric AEAD-encrypted UDP traffic using derived keys
```

### Key Exchange Details

The tunnel key exchange combines two algorithms for post-quantum security:

```md
1. Client generates X25519 ephemeral keypair
2. Client generates ML-KEM-1024 encapsulation
3. Both are sent to VPN server alongside the signed connect request
4. Server generates its own X25519 keypair and ML-KEM-1024 decapsulation
5. Server signs its X25519 public key with its private key
6. Both sides derive shared secrets from X25519 ECDH and ML-KEM-1024
7. Shared secrets are combined to produce the symmetric encryption key
8. Post-handshake: all key material is zeroed from memory
```

# WireGuard Mode (Optional)

In addition to the native protocol, Tunnels supports WireGuard as a parallel VPN protocol via a separate `wg-server` binary. This allows standard WireGuard clients (Android, iOS, desktop) to connect without custom software.

```md
- WireGuard peers are managed through the `/v3/wg/*` API endpoints
- The `wg-server` binary syncs peers from the controller every 30 seconds
- Key exchange: Curve25519 ECDH (Noise protocol framework)
- Data encryption: ChaCha20-Poly1305 AEAD
```

See the WireGuard integration guide for setup details.
